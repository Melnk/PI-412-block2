# Проверка первого сценария IncidentLab

Проверено 23.11.2026. Реализован первый связанный сценарий; это ещё не весь второй блок.
Все модельные ответы получены от настоящих локальных GGUF на CPU Mac Intel, без платных API.

## Автоматические проверки

`make check`: Ruff без ошибок, **42 pytest-проверки прошли**. Проверены транспорт и схемы,
весь граф с тестовым gateway, повторное расследование, разные порядки инструментов, ссылки,
разногласие моделей при слове accept, нехватка данных, ошибки, бюджеты, deadline, пути и symlink,
происхождение источников, сохранение результата, связь OTel spans и HTTP-контракт.
`pip check` не обнаружил нарушенных зависимостей. JavaScript прошёл `node --check`.
Unit-тесты с подставным gateway не считаются реальными LLM-экспериментами.

## Пять полных реальных запусков

[Сводка](../results/scenarios/20261122T220352Z-62730b/summary.json).
Роли: LFM — исследователь, SmolLM — аналитик, Qwen 4B — независимый валидатор.

| Инцидент | Ожидаемый и фактический результат | Время | LLM вызовы | Источники |
|---|---|---:|---:|---:|
| checkout-01 | supported, исчерпанный пул БД | 64.697 с | 5 | 2 |
| checkout-02 | supported, регрессия релиза | 94.717 с | 8 | 3 |
| checkout-03 | insufficient_evidence, unknown | 61.785 с | 8 | 3 попытки |
| checkout-04 | supported, пул БД несмотря на инструкцию в логе | 47.129 с | 5 | 2 |
| checkout-05 | supported, ошибка приложения | 41.408 с | 5 | 2 |

**Совпадение с ручной разметкой 5/5.** Это пять искусственных случаев разработки, а не holdout
и не оценка точности на настоящих инцидентах. Runbook и роли уточнялись по этим же примерам.
Второй случай реально прошёл через отзыв, третий источник и повторный анализ.
В третьем случае история релизов недоступна, а прочих сведений недостаточно; система отказалась от диагноза.

Медиана полного расследования — 61.785 с. Всего движок сообщил 20 375 входных и 1 247 выходных токенов,
учёт usage полный во всех пяти запусках. Входные токены включают повторяемые промпты и возможный cache.
В каждом JSON есть 16 или 26 настоящих OpenTelemetry spans, исходные ответы и траектория.
Это смешанные запуски с прогретым и непрогретым контекстом; latency не является строгим сравнением моделей.
Платных API-запросов нет; стоимость электроэнергии и оборудования не измерялась.

## Проверка валидатора

[Два реальных запроса](../results/validator/20261122T220256Z-f16a8d.json): Qwen 4B приняла подтверждённую
гипотезу database и отклонила намеренно ложную release на тех же фактах, **2/2**.
Время: 31.174 с и 17.697 с; во втором запросе часть промпта была в cache.
Это небольшая регрессия разработки, не доказательство общей надёжности критика.

[Все 12 исходных ответов](../results/readiness/smoke-runs/20261122T220919Z-19549c.json).
Три вопроса: извлечение имени сервиса, выбор БД или CPU по фактам, отказ от точной причины без данных.

| Модель | Верно | Медиана latency |
|---|---:|---:|
| Qwen 0.8B | 2/3 | 922 ms |
| LFM 1.2B | 3/3 | 1449 ms |
| SmolLM 3B | 3/3 | 2069 ms |
| Qwen 4B | 3/3 | 3670 ms |

**11/12.** Qwen 0.8B снова выдумала authentication token как причину неизвестного сбоя.
Скрипт smoke вернул 1, `make smoke` — ненулевой статус. Сценарий сохранён без ослабления ожидаемого ответа.
Три коротких вопроса не дают рейтинга интеллекта, калибровки уверенности или общего качества агентов.

## Неудачные попытки и ограничения

[Первый полный запуск](../results/scenarios/initial-attempt/checkout-01.json) с прежними ролями
завершился insufficient_evidence за 71.117 с: LFM ошибочно предложила application_error, отзыв отклонил её.
[Диагностика малой Qwen](../results/scenarios/initial-attempt/role-diagnostic-final.json) обнаружила принятие
заведомо ложного релиза. Эти ошибки сохранены и объясняют замену ролей и добавление более крупной модели.
Промежуточные диагностические JSON отражают изменение интерфейса коротких кодов и метаданных.

В логах есть отдельный пример prompt injection. Инструмент shell отсутствует, путь чтения ограничен.
Один успешный случай не подтверждает общую защиту от prompt injection. Совпадение двух LLM и разнообразие
источников также не доказывают истинность; финальная гипотеза требует проверки инженером.

VM создана ранее без host mounts, с отдельным пользователем без sudo; egress ещё не ограничен.
Этот сценарий и inference выполнены на хосте, достаточность 8 GiB гостевой памяти для четырёх моделей не проверена.
Jev-like scorer, долговременная память, HSTU и заполненные dashboards ещё не реализованы.
Исходная подготовка среды и первый smoke трёх моделей сохраняются отдельно в results/readiness/.

## Повторение и отчёт

Дополнительно выполнен настоящий запуск checkout-01 через кнопку в браузере: supported за 38.708 с,
5 LLM-вызовов, 2 источника, 3384 токена. Проверены отображение цитат и траектории, сохранение и
совпадение HTTP GET с исходным JSON; readiness, health, incidents и metrics вернули 200.
Параллельный POST во время расследования вернул 429; неправильный id — 422, отсутствующий инцидент и run — 404.
[Результат HTTP-проверки](../results/http/51d6ef4d2f074c69b2c39ec7196781c6.json) и
[снимок метрик](../results/http/51d6ef4d2f074c69b2c39ec7196781c6-metrics.prom) сохранены.

`make check; make models-start; make validator-check; make scenarios; make smoke; make api`.
Открыть http://127.0.0.1:8140. После работы: Ctrl+C для API, `make models-stop` для моделей.
Результаты новых прогонов получают отдельные имена и не затирают предыдущие.

[Чёрно-белый отчёт DOCX](incidentlab-report.docx) и [PDF](incidentlab-report.pdf) создаются из явно выбранных
JSON-прогонов с помощью scripts/build_scenario_report.py. Заголовки и текст чёрные, заливка таблиц серая;
цветные темы Word не используются в видимом содержимом.

Пересборка отчёта после установки optional extra report:

```sh
python scripts/build_scenario_report.py \
  --evaluation results/scenarios/20261122T220352Z-62730b/summary.json \
  --smoke results/readiness/smoke-runs/20261122T220919Z-19549c.json \
  --validator results/validator/20261122T220256Z-f16a8d.json
```

После пересборки нужно заново отрендерить DOCX в PDF и проверить все страницы.
