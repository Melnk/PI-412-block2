# Быстрый порядок реализации

## Подготовлено

- [x] Индивидуальное ТЗ и исследование источников.
- [x] Отдельная структура двух независимых пакетов: IncidentLab и RecSys.
- [x] Python-окружение, зависимости, Ruff, pytest и CI.
- [x] Проверенные GGUF и движок, локальный запуск трёх моделей, исходные ответы.
- [x] Служебный API и метрики процесса.
- [x] Конфигурация отдельной VM; ограничения готовности описаны в infra/README.md.

## Первый рабочий сценарий

1. Создать 3 небольших инцидента: БД, релиз и недостаточно данных; разметку держать отдельно от tools.
2. Инструменты чтения метрик/логов/релизов, с источниками и временем, без shell.
3. Связанный LangGraph: исследователь → аналитик → валидатор → заключение; условный запрос дополнительного факта.
4. Сохранять один trace, сырые ответы и траекторию; ограничить число шагов и токены.
5. Реальный запуск одного случая, затем отказ при нехватке данных. Моки не считаются этой проверкой.

## Следующий проход

6. Jev-like scorer: независимые шаблоны train/val/test, вероятности, calibration, fallback.
7. Три слоя памяти, TTL и обновление инструкции; пользователь агента внутри VM, egress и негативные тесты доступа.
8. Phoenix, Prometheus/Grafana, реальные метрики токенов/latency/CPU/RAM, пример алерта.
9. Отдельно RecSys: временной split, четыре baseline, маленькая HSTU, три seed и ablation; реальные метрики.
10. Полные evals агентов, одиночной LLM и версии без валидатора; исследование ошибок и уязвимостей RecSys.
11. Семь C4, два Sequence, PDF, чистый запуск и репетиция.

Реализация агента и RecSys не связывается в один продукт. Пока не нужны отдельный frontend framework,
авторизация, Kubernetes, внешние сервисы и интеграции с настоящими серверами. Нельзя сокращать требования
о трёх LLM, независимой валидации, памяти, evals или наблюдаемости ради скорости.
